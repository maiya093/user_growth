## 〇、这道题考什么

题目是通用的（单据 + 报表 + 大屏），岗位是**内部 ERP**，公司做**换电 / 租电运营**。我的判断是：

> **技术结构必须通用（证明会写 Frappe），业务语义必须贴公司（证明懂这家公司在做什么）。**

因此做了**一处关键重构**：把"用户服务开通 / 流失"从泛 SaaS 订阅，映射为换电业务的"**租电套餐开通 / 中止**"。题目要求不变，字段语义变成本行业的。

| 概念 | 泛 SaaS | 本项目（换电业务） |
| --- | --- | --- |
| 服务开通 | 签约生效 | 客户签约租电套餐，**电池出柜** |
| 服务流失 | 取消订阅 | **中止租电、电池归还入柜** |
| 计费 | MRR | 月租 × 租期 × 电池数 |
| 服务载体 | 软件席位 | **电池（4830/6030/6045）+ 换电柜站点** |
| 维度 | 套餐 / 渠道 / 地区 | **电池型号 / 城市站点 / 客户类型 / 租期** |
| 流失原因 | 价格 / 功能 | **单价过高 / 站点太远 / 电池老旧 / 车辆淘汰** |

## 一、业务背景与痛点

换电业务是**重资产租赁**：一次"流失"不只是收入减少，还意味着实物电池要回流入柜。而这类信息往往散落在 CRM、工单、客服记录、财务退款四个系统里，导致：

| # | 痛点 | 影响 |
| --- | --- | --- |
| P1 | 开通与中止无统一单据 | 无法回答"这个客户到底算不算流失"，口径扯皮 |
| P2 | 中止原因不可归因 | 只能看到"少了多少"，看不到"为什么少" |
| P3 | 只看总量不看结构 | 不知道哪个城市、哪种电池在漏，投放无法评估 ROI |
| P4 | 报表靠人工导数 | 周会前一天在拼 Excel，决策滞后 |
| P5 | **电池回收无闭环** | 中止了但电池没回柜，资产在流失而账上无感 |

## 二、目标与范围

| 目标 | 可验收标准 |
| --- | --- |
| G1 数据统一 | 报表与大屏所有数字**只有一个聚合函数出口**（`utils/analytics.py`） |
| G2 录得进 | 干净站点 `install-app` 后即有 1,500+ 条可信演示数据 |
| G3 算得对 | `期末在租 = 期初在租 + 新增 − 中止` 恒等式在任意过滤条件下成立，并有单元测试 |
| G4 看得懂 | 非项目参与者在大屏前 10 秒内说出"这个月是扩还是缩、漏在哪" |
| G5 贴业务 | 每个字段、每个维度都能对应换电运营的真实动作 |

**不做（及原因）**：电池库存 / 换电柜设备台账（ERPNext 标准模块已覆盖）、押金收退与账单（需真实科目体系）、BMS / IoT 对接（无设备数据源，无法自证）、移动端适配（大屏场景明确）。

## 三、方案选型（核心决策章）

### 3.1 三件套实现方式

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **Frappe 原生三件套**（DocType + Script Report + Page） | 零外部依赖、权限打通、`install-app` 一键复现 | 图表需自己写前端 | ✅ 采用 |
| 单据在 Frappe，报表外挂 BI | 拖拽分析强 | 评审方装不起来，且"Report / Page"两个考点被绕过 | ❌ |
| 纯 Query Report（SQL） | 快 | 承载不了图表与指标卡 | ❌ |
| 改造 ERPNext 标准 DocType | 少写代码 | 升级易冲突，看不出建模能力 | ❌ |
| 独立 SPA + API | 体验好 | 引入 Node 构建链，脱离 Frappe 生态 | ❌ |

```
Page（大屏，裸 JS + ECharts）
  └─ frappe.call → utils/analytics.get_dashboard_snapshot()
Report（Script Report，图表 + 明细 + 指标卡）
  └─ import utils/analytics
        └─ frappe.db.sql → DocType: User Service Record
```

> 报表与大屏**不各自写 SQL**，共同调用 `analytics.py`——**用代码结构保证口径一致，而不是靠人自觉**。

### 3.2 单据建模：一张表还是两张表

开通与中止字段重合度约 80%。拆两张表意味着报表两次 JOIN、Mock 与校验代码翻倍。用 `record_type` 区分后，**一次聚合同时拿到"进"与"出"**。
生产版演进：`Customer` / `Station` / `Battery` 独立主数据 + 变更单，形成生命周期链。

### 3.3 大屏技术要求

| 项 | 方案 | 理由 |
| --- | --- | --- |
| 分辨率 | 1920×1080 基准 + `transform: scale()` | LED 拼接屏分辨率各异，等比缩放不错位、无滚动条 |
| 前端 | 裸 JS + ECharts（Frappe 内置） | 避免 Node 构建，保证装完即跑 |
| 刷新 | 60s 定时 + 失败保留旧数据 | 大屏最忌讳"刷新时白一下" |
| 数据 | 单接口返回快照 | 8 个区块各发请求会出现"部分刷新"的割裂感 |

## 五、口径定义（口径唯一是这份 Demo 最在意的点）

| 指标 | 公式 | 回答什么问题 |
| --- | --- | --- |
| 在租客户 | `customer_code` 去重，期内开通 − 期内中止 | 现在手上多少家 |
| 新增 / 中止 | 按开通日 / 中止日落入月份，仅 `docstatus=1` | 这个月进多少、出多少 |
| 净增长 | 新增 − 中止 | **这个月是扩张还是收缩** |
| 期末在租 | 期初 + 新增 − 中止 | 存量变化 |
| 中止率 | `当月中止 ÷ 期初在租`；期间合计用 `期间中止 ÷ 期初在租`（**不按月相加**） | 客户在加速流失吗（期初为 0 显示 `—`） |
| 新增 / 中止月租 | `月租 × 电池数` 累加 | 收入净流入还是净流出 |
| 在租电池 | 期末在租客户的电池块数累加 | 资产投出去多少 |
| 未归还电池 | 中止单中 `battery_returned = 0` 的块数 | **有多少电池没回来** |

**约定**：客户口径（家）与资产口径（块）严格分离，"1 个客户租 20 块电池"不能算成 20 个客户；取消提交的单据不计入统计；金额单位 CNY/月，前端 ≥ 10000 显示"x.x 万"。

> **可讨论点**：中止率分母有期初 / 平均 / 期末三种主流口径，本项目选**期初**（分母稳定、月度可比）。这是面试时可主动抛出的 trade-off，也可以反问对方内部 ERP 现在用哪种。

## 九、面试沟通策略

### 9.1 这个 Demo 在回答面试官的哪些疑虑

| 疑虑 | 回答 |
| --- | --- |
| 只会写页面，不懂 ERP 里单据与数据的关系？ | 单据有校验/状态/锁字段，且考虑**资产回收（电池归还）**，体现台账思维 |
| 报表能不能被业务真的用？ | 维度对齐真实管理视角（城市、电池型号、渠道），指标带"回答什么问题" |
| 大屏是不是套模板？ | 8 区块每块只回答一个问题；单接口快照保证一致性；等比缩放适配 LED |
| 懂不懂 Frappe 生态？ | 全程原生三件套，并说明为什么不用 BI / Query Report / 改造标准 DocType |
| 代码能不能维护？ | 单一聚合出口、可幂等造数、可单测、README 有决策摘要 |
